## Question and scope

Does removing latest-stream queue array replacements improve end-to-end **publisher state replacement/publication through final stream consumption** on Node 22.23.3, Linux x64? This is a bounded first screen before broader runtimes, not an application speed claim. It supersedes the broader prospective matrix and baseline-only pilot in `latest-stream-allocation.md` for this first screen; the old file remains frozen evidence.

Exactly six cases are declared in `latest-stream-screen.manifest.json`: shared/copy transport, each crossed with one paused stream and 32 updates, four paused streams and 4,096 updates, and four continuously waiting streams and 4,096 updates. A single real Node Worker hosts one reader and its independent streams; the main thread publishes. Four streams are four independent iterators on that reader, not four workers or readers.

Publisher options are explicitly `delivery: 'all'`, `maxPending: updates`, and `timeoutMs: 30000`. One frame can be in flight; remaining frames drain through the package's ordinary ACK/backpressure path. All synchronous publications must reach the reader. No extra per-frame request, acknowledgement, timer, or yield is inserted. This is deliberately a lossless-publication diagnostic: default publisher delivery can coalesce the 4,096-publication burst down to two reader callbacks and would fail the workload promise. The streams themselves use `reader.snapshots()` with unchanged defaults: latest mode and initial emission enabled. Neither transport implementation nor the stream API is instrumented.

## Fixed input and timing boundaries

Build a 256-entry numeric SharedMap once before the session, then derive a second immutable map with key0 changed from 0 to 1. Repeated bursts alternate those same two immutable snapshots with `owner.publish(odd/even)`. Every call changes publisher state, captures the new state and commits one version. Snapshot construction is **outside timing**; this screen does not measure newly allocated immutable map updates. This narrower choice is intentional: historical arena growth and progressively larger copy payloads cannot differ between variants or later batches. The pool has exactly two inputs, every burst has an even update count and finishes on the original snapshot. Retain the initial reader snapshot for the entire subject and validate its size, key0 and key255 after every burst.

Each burst uses one arm/ready exchange before timing. The parent samples `process.hrtime.bigint()` immediately before the first publish. The worker records its timestamp immediately after all streams have consumed the final expected value, before assertions, stream termination, serialization, or the completion message. Node/Linux hrtime uses the process-wide monotonic clock; subtraction is in bigint before conversion to milliseconds. Each completion timestamp must lie between the parent's start and reception timestamps. Completion transport and validation are excluded. The end timestamp includes ordinary consumer continuations and the final `Promise.all` continuation. Worker startup, handshake, imports, fixtures, stream construction and initial waiting-stream consumption are outside timing.

For paused streams, a subscription resolves a promise on the final delivered version, and consumption resumes in a microtask after all final notify listeners finish. Every stream then consumes only that final snapshot. For waiting streams, consume initial version 0 (or the burst's start version) before ready, call next immediately, and rearm next immediately after each returned snapshot. Normal ACK delivery gives continuations an opportunity to rearm before the next message turn. Any missing, duplicated, reordered, or extra version fails correctness; it is never treated as a faster equivalent workload.

A subscription maps every actual snapshot wrapper to its delivered version using a WeakMap. Preallocated numeric buffers record all delivered versions/values and every stream's consumed versions/values. This verification bookkeeping is within the interval and is identical for both builds; its allocation and lookup costs may dilute the queue effect. Traces never retain the full sequence of snapshot wrappers. Assertions, array conversion, JSON output, and file writes occur after the timestamp. Paused traces explicitly list the overwritten initial version separately from delivered update versions 1 through N−1. Waiting traces must consume every delivered version with zero overwrites. An independent controller validates the complete raw trace again.

Every subject is a fresh Node process containing a fresh worker and exactly one selected build at the same neutral physical directory and fixed shared.js/worker.js paths. The entire original package.json is copied unchanged; imports use the public `zerocopy` and `zerocopy/worker` package exports. No symlink, variant-specific import URL, rewritten chunk name, variant label, Git SHA, or source-root argument enters the subject. Only persistent Node compile caching is disabled. JIT settings remain defaults. Physical-path, package, source, bundle, before/after staging and executable receipts are retained for each subject. The canonical directory is preserved for failure review.

## Calibration and fixed experiment

Both variants receive disposable pilots for each case before measured subjects. Each pilot first runs two one-burst warmups, then up to eight calibration steps with three batches per step. A batch is the sum of complete publication-to-consumption intervals for a fixed number of bursts, not a continuous wall interval; round setup, reporting and validation are excluded between bursts. Start with one burst, grow toward a 30 ms minimum across all three pilot batches, and cap at 256 bursts. This declared pilot adaptation is the only timing-dependent work selection. Cap flags and every pilot trace/sample remain in the artifact. The measured work count is the larger of the two pilot counts, fixed equally for both variants and both roles of baseline A/A.

Each measured subject has two warmup batches and seven measured batches with that same fixed count. At least 20 ms summed timed work is required in **every warmup and measured batch**. Short batches and capped pilots invalidate inference, remain visible, and never trigger timing-driven retries. Subject timeout is 180 seconds; failed/partial output is retained. No sample removal, outlier filtering, extra quartets, favorable-cell reruns, or runtime expansion is allowed within this screen.

Per case: four A/B quartets and four baseline A/A quartets, each with four fresh processes. Each mode has exactly two ABBA and two BAAB orders. The mode that goes first is balanced two/two across quartets; the seed is fixed. A means baseline; B means candidate in A/B and an independently launched copy of the identical baseline in A/A. All six cases execute serially in the predeclared order on one runner. No other tests, measurements or browser jobs execute concurrently on that runner.

## Estimator, controls and decision

For each subject, take the median of its seven batch times per burst. For each adjacent A/B or B/A pair, calculate log(B latency/A latency). Average the two adjacent pair log ratios within a quartet. The reported estimator is exp(mean of the four quartet values), with a two-sided 95% Student-t interval, df=3, critical value 3.182446305284263. The independent inference unit is the quartet, not the seven samples or individual bursts. Report raw absolute subject medians, all pair/quartet values, and all six pointwise intervals; no pooled headline or simultaneous-confidence claim.

The predeclared latency margin is 2%. A/B lower CI >1.02 is a material slowdown signal; upper CI <1/1.02 is a material improvement signal; upper CI ≤1.02 otherwise supports only the stated regression bound; otherwise the result is inconclusive. A/A control drift means its point estimate is outside [1/1.02,1.02] **and** its CI excludes 1. It invalidates that cell and never normalizes or adjusts A/B. Absence of that flag does not establish control equivalence or stable noise: show the full A/A interval, especially a wide interval crossing 1. A preliminary improvement signal is not sufficient to publish an application speed claim. A credible next-stage decision requires meaningful improvement in paused cases, no >2% waiting-case regression, valid controls, complete source/correctness checks and appropriate interval precision. If noise masks the effect, retain only the narrow allocation-mechanism statement.
