# Existing JavaScript UTF-8 JSON parsers

Research checked on 14 November 2026. This is source inspection, not a package performance measurement.

## @jsonjoy.com/json-pack 18.30.0

This is a credible direct-byte parser to consider: its documented API is new JsonDecoder().decode(uint8Array), imported from @jsonjoy.com/json-pack/lib/json. It reads structure from bytes and creates ordinary JavaScript values. The package offers several serialization formats and extensions.

However, **the published 18.30.0 JsonDecoder cannot replace ZeroCopy's JSON.parse path without compatibility work.** The following findings were checked in package/lib/json/JsonDecoder.js extracted in memory from the exact npm tarball, not merely from an older repository checkout.

| Case | Published source behavior | Why it matters here |
| --- | --- | --- |
| Unicode escape in a string value, including "\ud800" or "\u0000" | readStr() decodes the UTF-8 span and replaces only short escapes; it has no \uXXXX processing | JSON.stringify legitimately emits Unicode escapes for lone UTF-16 surrogates and some control characters. Leaving the escape text in the returned string changes the value. |
| Unicode escape in a property name | readKey() has cases for short escapes but no u case; the default throws | A property name containing an escaped control character or lone surrogate is legitimate writer output. |
| Own property named __proto__ | readObj() rejects this key explicitly | Native JSON.parse creates an own data property. ZeroCopy already tests preservation of this behavior. |
| A string beginning with the package's binary data-URI marker | readAny() tries binary decoding and can return Uint8Array | This is intentional format-extension behavior, but it changes a normal JSON string's type. A separate CBOR marker can produce undefined. |
| Extra bytes after the root value | decode() resets its reader and returns readAny() without an end check | It is not a whole-input validator equivalent to JSON.parse. This is less relevant for trusted writer-generated bytes, but matters when describing parser compatibility. |
| Number tokens | Short tokens are assembled as a small string and converted with unary +; the implementation is unrolled through 24 characters and then throws | The conversion uses JavaScript's number semantics, but arbitrary longer JSON tokens do not have native parser behavior. Ordinary JSON.stringify number output is a narrower case. |

The key source fragments are:

    const REGEX_REPLACE_ESCAPED_CHARS = /\\(b|f|n|r|t|"|\/|\\)/g;

    if (key === '__proto__')
        throw new Error('Invalid JSON');

These are **compatibility differences for ZeroCopy's particular contract**, not a claim that the package is unusable for its supported formats. Its documentation and source explicitly provide binary extensions. Benchmarking it as an equivalent drop-in on a fixture that omits these cases would not establish that equivalence.

No package was installed, no production source was modified, and no package benchmark was run. Exact example outcomes above are inferred from the inspected source; they are not claimed as executed package tests.

## Another candidate for a separate evaluation

@streamparser/json 0.0.26 is a general streaming UTF-8 parser with Uint8Array input and a JSONParser callback API. Its project describes JSON.parse compatibility, and its number conversion defaults to Number(numberStr). This is designed for incremental input and selected paths rather than a reusable synchronous decode(bytes) method.

It was not installed or audited sufficiently here to establish compatibility or performance on ZeroCopy's full contract. It remains an optional independent implementation to evaluate if generic byte parsing is pursued further.

- Pinned package metadata: <https://registry.npmjs.org/@streamparser%2fjson/0.0.26>
- Official repository: <https://github.com/juanjoDiaz/streamparser-json>
- API guide: <https://github.com/juanjoDiaz/streamparser-json/blob/main/packages/plainjs/README.md>

## Implication

Direct parsing is already possible in JavaScript; it does not require moving ZeroCopy to Rust. Existing direct-byte libraries also need semantic review and whole-pipeline measurement. The negative measurements of the local prototypes remain findings about those implementations, rather than a universal limit on direct UTF-8 parsing.
