# Finite hosted preparation for the empty-prefix screen

Status: v2 prospective preparation plan for independent review; v1 is preserved.
This successor changes only the first-run activation route to the existing
branch-push mechanism. No wrapper has been
implemented or executed under this plan. The final ordinary composite, driver
review, exact input bytes and coordinator release must be bound before publication
or subject execution. This plan does not change method v5 or its 400-child screen.

## Boundary and reuse

Prepare two separate source/output roots and the already specified Node 22.16.0
and Bun 1.4.2 toolchain, then invoke the reviewed hosted adapter exactly once.
The screen retains its independent 600-second deadline, starting before its first
validation diagnostics and including all 400 subjects, analysis and final hashes.
Provisioning is explicitly separate. No setup work is charged to, or grants extra
time to, the screen. No extra subject-import, lookup, startup or calibration probe
is added during preparation.

Reuse the finite command supervisor, locked dependency installation, exact source
archive/patch verification, portable-core authentication and output inventories
from the completed ordinary-correctness preparation. Reuse WNOWAIT ownership,
terminal cap checks and durable partial receipts. Do not import its correctness
command list, rerun ordinary tests, or construct a new execution framework.

Proposed limits for preparation only: 900 seconds total, with the last 60 seconds
reserved for cleanup and partial-artifact preservation; 4 GiB sampled process-group
RSS plus terminal high-water checks, and at least 5 GiB MemAvailable at entry.
These reuse the ordinary gate's memory policy. Every command has its listed cap
and is also bounded by the remaining preparation work budget. The active process
group is killed on deadline/interruption; no retry or automatic fallback occurs.
Sampled memory is not a hard cgroup guarantee. All preparation descendants are
owned, inspected and cleaned before leader reap; no group overlaps the screen.

## One preparation sequence

1. Check repository, Linux x64 host, attempt 1, reviewed proof head and sole parent.
   Authenticate every input and implementation file. Record host and memory.
2. Copy the unchanged toolchain package/lock. Run the ordinary gate's `npm ci
   --ignore-scripts --no-audit --no-fund` once against the official registry, with
   a 180-second cap. Verify Node/Bun version, binary hash and identity using the
   existing bounded runtime-only commands (5 seconds each). Use the same sanitized
   environment and executable paths throughout. No dependency version updates.
3. Archive the exact main commit once (30 seconds), safely extract it to two new
   arm directories, verify both as the exact 502-source baseline, then check/apply
   the fixed patch only in the candidate (10 seconds each). Verify the candidate
   as exactly 503 sources and the baseline unchanged. Link the same locked
   dependency tree for builds. No Git context is needed inside these arm roots.
4. Build baseline native outputs (90 seconds) and portable outputs (60 seconds).
   Compare the resulting complete 25-output inventory byte-for-byte with the
   authenticated baseline manifest. Record all native build inputs and prove
   they match current baseline sources and the common native-output manifest.
5. Build candidate native outputs (90 seconds), portable outputs (60 seconds),
   and declarations (60 seconds), using exactly the ordinary gate's commands.
   Compare the complete 66-output inventory with both ordinary stage manifests.
   Declaration outputs are included to preserve exact correctness provenance;
   neither engine loads them. No extra baseline declaration build is introduced.
6. Authenticate the portable import graph and embedded persistent-core bytes in
   each arm. Require equality to each arm's Bun-loaded core and equality between
   arms. Verify all static source closures, source/output inventories and public
   entry hashes. Recheck source trees and executable hashes after all builds.
7. Validate the truthful ordinary composite with the driver's existing pure
   authentication function. Freeze preparation receipts and final arm descriptors.
   Materialize the reviewed execution-pin and release templates using only the
   verified absolute paths and reviewed proof head; all content hashes, evidence
   identities, method, implementation and 400-subject scope are already fixed.
   The wrapper cannot approve new outputs or replace missing evidence.
8. End preparation successfully only after owned cleanup and final authentication.
   Invoke the existing adapter in a separate screen step, once, only when the
   coordinator has released the complete reviewed packet. A failed preparation
   produces partial evidence and no subject child.

The wrapper has finite build/installation command counts, no retry loop, no
subject imports and no measurements. It does not add validators or runtime probes
to the screen. The driver performs its existing in-process clock diagnostics and
public resolution checks within the unchanged approved cohort.
