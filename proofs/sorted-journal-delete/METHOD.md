## Question and scope

Does a complete public `SharedSortedMap.delete` benefit when its key is pending in a normal sorted update journal? The candidate omits every byte-equal target entry, removes any older canonical-base version, and immediately folds all survivors. It retains the existing wrapper, lookup, native size calculation, allocator, fold ownership mark, and canonical result. It adds no retained journal or later reader work. The pristine efficient baseline materializes the complete journal and then removes the key.

Admit only the reviewed native `radixDelete` change: a bounded one-level journal, canonical-or-zero base, valid allocated pending leaf, exact query/key-pointer identity, correct length and overflow-safe allocated-range guards, and full byte filtering independent of stored hashes. Ineligible inputs retain the literal old route. Also retain that route when zero survivors remain and removal leaves the same nonzero nonleaf base. This preserves prior-root equality and net-zero session notification behavior. The primary has three survivors, so this guard does not remove its opportunity.

There are two separately declared possible leads: a latency lead under the fixed 5% rule, and a deterministic native-allocation lead under the fixed 10% rule below. Neither implies an application-wide benefit or publication readiness. The existing documentation's `SharedMap` memory chart does not exercise this sorted-delete path; it supplies no matched evidence here. Native append-only used bytes, backing capacity, retained memory, and RSS are different quantities.

## Fixed fixtures and eleven rows

All maps are numeric and naturally sorted, with no custom comparator. Define `K(i)` as `k` followed by exactly four lowercase hexadecimal digits. Canonical template T contains `K(0)` through `K(4095)`, each with value i. Template S contains `K(0)` through `K(15)`, also valued i. Template G contains `aa:0, ab:1`. Template L uses T's values and keys prefixed by exactly 1,024 ASCII `p` characters.

Construct each template through public `set` calls in a fresh writable arena obtained by public `compact(new SharedSortedMap('number'))`, then public `compact` again to obtain its canonical template. No fixture-building deletion is allowed. Release builder snapshots and all builder-buffer references after validation; they are distinct from the retained compacted templates. The module-global default arena remains empty: never perform construction writes through it. Record its zero payload and initial backing capacity separately. Before any collection construction, call public `configureMemory({maximumBytes:134217728})` once. This 128 MiB per-arena limit is a resource ceiling, not preallocation. Retain the four canonical templates for the child lifetime.

For each warm-up, pilot, or measured batch, make an independent fresh public `compact(template)` and apply the row's listed setup outside the clock. Every timed repetition starts from that same batch input; successful outputs are immutable forks, not an ever-shrinking map. Pending replacements use value `10000+i`. T/L replacement order is i = 256, 1024, 2048, 3072; S replacement order is 1, 4, 8, 12. The primary deletes the third pending entry, chosen before any observations.

| ID | Input and complete timed unit | Role |
|---|---|---|
| P | T + four replacements; `delete(K(2048))` | Sole latency and allocation primary; 4,096 keys, three surviving pending replacements |
| S16 | S + four replacements; `delete(K(8))` | Small canonical base, same pending count |

## Fixed arena lifecycle and source-derived allocation bounds

Drop all prior-batch snapshots, exported payloads, DataViews, memory/buffer references, and closures after validation; retain only scalar receipts and the canonical templates. Before constructing the next batch request exactly one synchronous explicit GC: `globalThis.gc()` under Node with `--expose-gc`, or `Bun.gc(true)`. After constructing and validating the fresh fixture, request exactly one more, then take its starting receipt and time the loop. Use this same schedule for every pilot, warm-up, and measurement in every arm. Verify API availability before calibration; no alternate collection policy is permitted.

This excludes fixture creation, compaction, semantic/shape checks, explicit reclamation of previous arenas, and setup GC from reported latency. Record their separate wall durations. It measures operation latency in a fresh prepared arena, not complete create/delete/reclaim throughput. Automatic GC occurring inside the loop, wrapper allocation, native append allocation, and memory growth remain in the elapsed time. Different native allocation and growth within the common lifecycle remain part of each arm's result. Forced collection does not prove memory was reclaimed; RSS remains independently bounded.

Source arithmetic supplies conservative operation limits, not observed costs. A radix branch uses `align8(16+4*children)`, at most 88 bytes for 17 digits. T has at most six discriminating nibble positions; adding K(4096)…K(4099) raises this bound to eight. S has at most two. L's common prefix changes key comparison length without adding branch positions. An insertion copies at most one branch per existing path level plus a splice branch; a removal copies at most one per level. At most four folds plus one removal occur per delete. X4 additionally allocates four 32-byte short-key numeric leaves and journals of 24, 24, 32, and 32 bytes. These bounds cover both ordering choices, without assuming the candidate allocates less.

|---|---:|---:|

Do not use a key-length-times-depth bound for L: its 1,024-byte shared prefix is compressed, while its comparison costs remain real.

Each prepared batch arena must use at most 8 MiB before timing.
