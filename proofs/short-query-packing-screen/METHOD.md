## Question and six workloads

Does removing two temporary packing arrays improve a useful public compile-and-use operation? Use SharedList.compileTextSearch and its returned index predicate throughout. The primary compiles each changing query once and calls it on 16 consecutive rows. One-row calls can still trigger a whole half-leaf scan; report that behavior rather than describing them as one native row search. There is no compile-only primary or claim of faster inner scanning.

Use one fixed, equally weighted eight-query cohort: sensitive `x`, insensitive `warn`, sensitive `café`, sensitive `GET /api`, insensitive `requestId`, insensitive `authorization`, sensitive `user@example.com`, sensitive `😀😀😀😀`. Their encoded lengths are 1, 4, 5, 8, 9, 13, 16 and 16 bytes. Each query has its own prebuilt immutable 4,096-row list, with deterministic distinct log-like records, alternating matching/nonmatching rows and matches at early/middle/late positions in a repeating pattern. Records have at least 64 UTF-8 bytes; insensitive short-query records are ASCII. Data, term strings and option objects are constructed outside timing. Freeze the exact corpus and expected checksums before any subject timing; neither arm may choose its data.

Six aggregate workloads, each a separate reported endpoint per engine:

1. P1: compile once, then test indices 0–15 for each short query. This is the sole primary.
2. S1: compile once, then test one alternating hit/miss index for each short query. Secondary evidence about the highest compilation frequency; it cannot replace a failed primary.
3. C1: compile once, then scan all 4,096 indices for each short query. This measures preparation amortized over a larger scan.
4. C2: scan those 4,096 indices using predicates compiled before warmup. This checks the reused-predicate path; all 4,096 rows are revisited, so the predicate's last-half-leaf cache cannot replace the scan.
5. C3: compile and test 16 rows for an equal mixture of 24-byte and 40-byte ASCII terms, exercising unchanged byte-skip and KMP preparation. Keep case modes and hit/miss proportions fixed.
6. C4: compile and test 16 rows for fixed Unicode fallback queries: insensitive `İ`, `Σ`, `ß`, and a sensitive isolated high surrogate against decoded astral text. This exercises unchanged decoder/JavaScript matching.

C3/C4 are cohort-level controls; clearance does not establish separate bounds for their individual terms. Check expected counts and an index-sensitive checksum against decoded-string JavaScript includes/toLowerCase outside timed regions. Within timing consume every predicate result into a checksum returned after the batch. Include compilation and closure allocation in P1/S1/C1/C3/C4, and natural GC costs. No forced GC, private native entry, dataset construction, assertion or result serialization belongs inside a timed batch.

## One bounded hosted screen

Prefer one economical hosted job because earlier long local screens suffered host pauses/recovery. Use the same pinned Node 22.16.0 portable `dist/shared.js` and Bun 1.4.2 source `shared.ts` routes as correctness, matched pristine/candidate sources, locked dependencies and identical native payloads. Authenticate emitted deltas and source/native/toolchain hashes. Record runner/CPU/OS identity. One setup allowance of 900 seconds and one screen allowance of 900 seconds; no automatic retry. Publication and the eventual exact driver/argv need separate review and release.

Use two baseline-only calibration children, one per engine, followed by 16 paired rounds per engine. Each round has one fresh baseline and one fresh candidate child running all six workloads: 64 measured children, 66 total. Alternate arm order AB/BA by round and alternate engine order. Rotate the six-workload order cyclically by round, identically within each pair. Preserve the predetermined ordering; never run engines or arms concurrently.

Calibration chooses a whole-cohort repetition count K separately for each workload/engine, shared by both arms. First run 500 ms of the exact public workload as unmeasured warmup. Starting at one repetition, double at most 20 times; at each level run eight untimed warmup batches, then three timed baseline batches of that same operation. Take the first K whose median reaches 50 ms; this K is never chosen from cold/import timing or another proxy operation. Retain every calibration observation. A 30-second calibration-child cap, 2-GiB sampled group-RSS cap or failure to reach that target stops the screen before candidate measurement. Calibration cannot inspect candidate performance.

At the frozen counts, every measured child runs the same 500-ms unmeasured workload warmup, then eight untimed warmup batches and four recorded batches per workload. The 500-ms phase immediately precedes each workload in both calibration and measured children; its operation is identical, including query compilation when the endpoint includes it. Use a monotonic high-resolution clock around the entire batch. Preserve all warmup durations, all four measured durations/checksums, raw stdout/stderr and exit/cleanup receipts. Bound each measured child to 15 seconds and 2 GiB sampled group RSS. The first doubling past 50 ms can approach 100 ms: six workloads then need about 6 × (0.5 + 12 × 0.1) = 10.2 seconds per measured child before setup, or 652.8 seconds across 64 children. The separate 900-second screen cap allows the two 30-second calibrations and bounded overhead; it does not add samples or permit retries. Actual pauses remain subject to the fixed child and whole-screen caps. Original process groups, including descendants, must be empty before their leaders are reaped. Terminal failures/cap breaches stop further execution and invalidate eligibility; preserve partial records. Safety durations and RSS are not performance or memory endpoints.

## Fixed decisions

For each workload/engine, take the arithmetic mean of all four measured batches within each child, divide by the fixed operation count, then form the 16 paired log(candidate/baseline) ratios. Ordinary slow/GC batches retain their full equal weight; medians may be reported descriptively only. Report the geometric mean ratio, paired-log standard deviation, within-child batch spread, and ordinary two-sided Student-t 95% interval over those 16 pairs. Do not pool engines or treat four batches as independent replicates.

An endpoint is quality-clear only if every measured batch lasts at least 20 ms, its ratio interval upper/lower is at most 1.20, and at least 14 of 16 children in each arm have the median of warmup batches 7–8 divided by the median of batches 5–6 within [0.90, 1.10]. Quality flags retain every observation and never erase adverse evidence. No outlier removal, extra rounds, changed counts after calibration, favorable resampling or source tuning follows observed results.

Promising primary: P1 is quality-clear and its ordinary 95% upper ratio is at most 0.95 in both engines. In addition, no completed valid endpoint may have an ordinary 95% lower ratio above 1.02: any such material-harm observation vetoes promotion even when that endpoint has a variability flag. A promising primary can justify investigating unresolved controls; it is not regression clearance. S1 or a pooled average cannot rescue P1.

Regression clearance within these six aggregate workloads additionally requires all 12 engine/workload endpoints quality-clear and every simultaneous one-sided upper bound at most 1.02. Report small adverse point estimates honestly; a point ratio above 1.00 is not a separate clearance defect when the stated 2% simultaneous bound is met. Use Bonferroni familywise 95% bounds across 12 endpoints, with Student-t quantile 1−0.05/12 and 15 degrees of freedom. Ordinary intervals govern the harm veto; simultaneous bounds govern clearance. Publish all endpoints and negative/inconclusive results. If primary or quality fails, park this fixed screen without rerunning it for a favorable result. A later change requires a new rationale and explicit review; it cannot overwrite this study.

## Claim limits and follow-on

The source avoids 32 bytes of requested typed-array backing payload per eligible compilation, plus engine-dependent objects/iteration. That is not a measured 32-byte heap reduction: allocator overhead, optimization, lifetime and GC differ by engine, and the predicate already retains neither temporary array. This screen has no heap endpoint and no dataset-memory claim. Existing documentation/website charts do not measure or imply this candidate's benefit.

Report source/emitted byte differences as static costs. Startup/import/attachment latency, browser speed, general heap behavior and full-suite compatibility remain untested by this screen. Only a promising useful result should trigger separately reviewed broader correctness/browser work before considering integration. The website compiles once per scan, so its large-scan behavior is represented by C1's amortization question, not by multiplying a small-query gain across all rows.
