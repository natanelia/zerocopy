## Observations and inspected APIs

The reporter reads the installed 4.1.11 Reporter/TestModule/TestCase interfaces. It records `onTestRunStart`, `onTestModuleQueued`, `onTestModuleCollected`, `onTestModuleStart`, `onTestModuleEnd`, `onTestCaseReady`, `onTestCaseResult`, `onTestRunEnd` and `onProcessTimeout`. Ready means before beforeEach hooks, not necessarily entry into the test body. Reporter timestamps are receive times; worker RPC buffering can delay them. Reporter objects do not expose worker IDs, so no worker assignment is inferred from them.

The worker observer subclasses the actual public VitestTestRunner, retaining every default method, return value and rejection. The inspected `resolveTestRunner` injects its module runner and wraps collection/update RPC for custom runners too. Direct worker JSONL captures before-collect, collection start/end, test-file import start/end, module start/end, test ready, per-attempt start and test result. It never replaces runTask/runSuite, assertion state, task metadata, globals, timers or module caches. It calls each overridden default exactly once. Module start is entry into the default before-suite hook, including snapshot setup; module end follows the default after-suite hook. BeforeTryTask records follow default assertion/snapshot preparation. A stalled import/default hook naturally leaves a start without an end.

Each direct record includes process PID, Node/Bun worker-thread ID, main-thread flag, current `VITEST_POOL_ID`, `VITEST_WORKER_ID`, wall time and monotonic timestamp. Vitest worker ID can change as a physical worker is reused; pool/thread identifiers provide the predecessor chain. Node threadId and Linux `/proc` thread IDs are different namespaces and are not equated. The exact declarations/implementations inspected are SHA-pinned: reporter declarations; CLI lifecycle/cache/pool implementation; default sequencer; runner declarations/implementation; worker-init environment assignments; runner interface and execution implementation; and default runner resolution/RPC wrappers.

Direct append-only JSONL writes are synchronous, small and unbuffered by JavaScript. Each worker/thread and observer has its own file. An external Node parent samples its own liveness/CPU plus every live process in the owned child process group and each Linux thread every 2 seconds; start/deadline/cleanup samples are also retained. Samples include state, CPU ticks, start ticks, RSS pages, thread counts, monotonic time and host load/uptime. The parent event loop is independent of the Bun worker event loop, so it can sample and enforce the deadline during a worker hang. CPU ticks are raw kernel counters; they are not benchmark measurements. There is no in-worker heartbeat timer to change scheduling.

## Fixed bounds, failure retention and interpretation

The full-suite command has exactly the original 600000 ms outer bound, separate from all unchanged test timeouts. Setup/version commands are bounded at 30 seconds; install and each build at 180 seconds; deterministic observer tests at 30 seconds. The workflow allows 50 minutes for the bounded command sequence and a 55-minute job including retention; these cover the maximum declared build/setup/suite bounds. Each child starts a new owned Linux process group. Deadline/interruption and command completion kill only that group; `/proc` cleanup must verify no live member within 1000 ms. Zombies are recorded but cannot run. Detached descendants that deliberately escape the group are outside this guarantee. A suite failure or timeout stays failed; the counterpart arm runs once only after verified cleanup. Interruption or integrity/setup/cleanup failure stops dependent work.

Raw stdout/stderr are open evidence files from child start. Parent samples and worker/reporter traces are append-only; atomic manifests persist pending and finished commands. Finalization hashes every available file, including truncated JSONL, followed by a complete artifact inventory, checksums, compressed archive and archive checksum. Always-run workflow retention also keeps partial outcomes. Host loss, SIGKILL of the parent, disk exhaustion or CI cancellation during artifact upload can still prevent a final receipt/archive; an absent/incomplete receipt never passes.

Instrumentation adds synchronous writes, module loads, promise continuations, parent sampling and small reporter/sequence work. A fresh cache also intentionally changes candidate scheduling versus the historical warm-cache run. These observer effects can hide or provoke a timing-dependent failure. A reproduced stall may locate collection/import/test/default-hook/reporting phase and its predecessor worker sequence; it does not alone establish causality. If no hang reproduces, historical cause remains unknown. Even two complete observed passes only admit separately reviewed future timing recovery; this diagnostic neither rehabilitates the original failed gate nor makes any speed, allocation or performance claim.
