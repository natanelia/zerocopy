# Moving-window reader baseline

Pinned post-#97 main: d57fc413ee5f67d0839f5a3a8ff36f4a51fb0341. This is a baseline-only proof branch, not a PR and not a runtime candidate.

Hypothesis: the first 2,048 decoded records can permanently exhaust the 2 MiB/2,048-entry object cache in a reader. A later small viewport or editor selection may repeatedly decode and freeze objects even though its working set fits the nominal cache. The first-root key cache also only retains accepted objects. The same runtime should behave differently depending on access history. Quantify before changing any runtime. Existing tests explicitly promise identity for admitted objects and non-retention after the limits; do not silently replace these semantics with LRU or alter public contracts. If this is substantial, investigate an internal non-retaining lookup/decode acceleration or an explicitly approved opt-in policy. Previous #75/#79/#86 investigated construction, freeze and selective reads; #68 scan traversal, #61 descriptor classification; this proof measures access-history dependence, not their claims. No changes to those PRs.

The test uses real Node worker threads and the website catalog fixture, 1k/10k/100k records, first-touch prefill of disjoint region (up to 4k), 12 repetitions of the same later hot region (up to 1k), sparse publication using initWorker(previous), verification of every returned value/deep freeze and retained old snapshots. Seven alternating measured pairs, warmup pair excluded, separate identical saturation A/A. Timing includes worker startup/first answer separately from subsequent hot query loops. Identity counts diagnose retention; measured heapUsed is an observation, not peak/RSS/GC proof. Saturation vs fresh is a workload contrast, not a code speedup; first-query work counts differ and must not be compared as equivalent. Verify raw artifacts and decide on a feasible next candidate; do not trigger duplicates or publish. Browser qualification and fair native controls will be needed if there is a runtime candidate.

## Completed access-history baseline — November 26

[Run 45728416438](https://github.com/natanelia/zerocopy/actions/runs/45728416438) passed. [Raw evidence](https://github.com/natanelia/zerocopy/actions/runs/45728416438/artifacts/15076225194) independently checked: all 96 raw JSON rows exactly match the log, all verified, seven measured pairs per cohort and size. Node 22.23.5. Median per-worker median of 12 repeated hot queries (not first-query comparisons):

| Records | Fresh | Saturated | Paired saturated/fresh | Saturated A/A |
|---:|---:|---:|---:|---:|
| 1k | 0.040 ms | 0.036 ms | 0.947x | 1.006x |
| 10k | 0.062 ms | 1.858 ms | 30.414x | 1.001x |
| 100k | 0.062 ms | 1.899 ms | 31.533x | 1.092x |

At 10k/100k the fresh reader reused 1,000/1,000 hot references per repeat; saturated reader reused zero. At 100k, after a sparse publication fresh reused 1,000 references; saturated reused zero (the hot region was unchanged in this fixture). Saturated repeat pooled p95 2.943 ms vs fresh 0.192 ms. This is an access-history cliff in unchanged code, not a measured optimization. Heap observations are not peak memory. Explicit tests in object-read-cache.test.ts and json-read-cache.test.ts require admitted identity and non-retention beyond caps; replacing default admission with eviction is incompatible. Existing #79 freeze study and #86 selective-field study should not be duplicated.

Next: [attribution script](./moving-window-reader-profile-20261126.mjs) uses the exact same pinned runtime in real Node workers and matched histories, alternating paired ordinary get and pre-resolved leafValue (diagnostic removal of key lookup only, not an API or candidate) plus identical get A/A. It verifies every result, deep freeze and distinct nested references after saturation. Separate CPU profiles of get and leafValue at 100k identify how much remaining time is spent parsing/freezing/decoding rather than lookup. Measure this before deciding whether a contract-preserving lookup improvement is worth its complexity or an explicitly opt-in cache policy is the only substantial opportunity. No production runtime edits, PR preview or publication. Do not rerun the completed history baseline.


## Completed lookup/decode attribution — 26 November

[Run 45735816575](https://github.com/natanelia/zerocopy/actions/runs/45735816575), [raw artifacts and CPU profiles](https://github.com/natanelia/zerocopy/actions/runs/45735816575/artifacts/15077909277). Independently parsed 98 JSON rows, exact log match; Node 22.23.5. Pre-resolving every leaf before timing improved saturated ordinary 1k-key reads at 10k by 1.228x (2.696 to 2.170 ms arm medians; A/A 1.025x) and 100k by 1.264x (2.695 to 2.155 ms; A/A 0.999x). The 1k admitted control is sub-0.07 ms and noisy. This is an optimistic diagnostic, not an implemented speedup. In the 100k ordinary get CPU profile, decodeAt and freezeJSON account for approximately 69% of sampled self-time, plus UTF-8 decoder overhead. Eliminating lookup alone cannot solve the 30x access-history cliff. Existing #79 already studied freezer traversal (rejected broad change), #86 focuses on selective fields and wide flat objects, so neither is a substitute for a moving-window policy.

Next screen: an explicitly enabled, experimental FIFO decoded-JSON policy on a fresh read-only reader. Default remains unchanged; no eviction is enabled without the proof-only method. Same 2048 record/2 MiB encoded JSON accounting limit; no secondary strong object-key references in adaptive path; existing bounded pointer cache adds possible metadata overhead. Never evict a nested handle. This is not an API proposal or a default behavior change; opt-in identity across eviction differs deliberately and must be documented if pursued. Test real Node workers, prefill, repeat, 50%-overlapping viewport shifts, return, uniform scatter/misses, sparse publication and old snapshot. AB seven measured pairs, AA and candidate-disabled controls three; all values/deep freeze, cache bounds, default admitted identity and old snapshot correctness checked. Heap readings are sampled observations, not peak resident memory; measure key metadata and mixed/nested/oversized cases before acceptance. No external release or Pages publication. The proof-only branch should not be merged or opened as a PR. If the opt-in screen is strong, qualify browsers and settle a safe opt-in contract before a focused production PR. No default eviction or API change without appropriate review/authorization.
