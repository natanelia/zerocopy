# Ordered-map temporary-storage screen, prospective v3

**Exploratory screen, chosen before execution. Preparation only; no driver or performance execution is released.** This can reject the candidate or identify a worthwhile, specifically bounded paused-iterator heap benefit. It cannot authorize production promotion or declare broad regression freedom. The focused correctness gate is reported green by its owner; its independent raw audit and any later ordinary correctness gate remain separate prerequisites.

## Comparison and seven cases

Compare unchanged main `afdffdcfcbd61013f120de82411c0c4a6b2d1e0e` with only the reviewed `SharedOrderedMap.entries` runtime patch. Bind both complete source manifests, generated portable modules, native artifacts, harness and exact executable hashes before execution. Node **22.16.0** imports public `dist/shared.js`; Bun **1.4.2** imports public `shared.ts`. Use the same fixture code and public operations in both arms. No baseline instrumentation, artificial allocation, disabled cache, alternate algorithm, private-field modification, engine comparison or block-size tuning.

All keys are `event:` plus the six-digit, zero-padded decimal index. Numeric values are the index. The primary represents a stable, insertion-ordered index of 100,000 records. These are seven deliberately different questions, not a parameter matrix:

| ID | Fixture | Question |
|---|---|---|
| P | 100,000 numeric entries, all live, original insertion order | Primary paused-iterator retained heap and large stable traversal |
| E0 | Empty numeric map | Added routing cost when checkpoint storage is unused |
| F128 | 128 numeric entries; overwrite every fourth key with `i + 1,000,000` | Small nonempty filtering traversal on the unchanged below-threshold path |
| F513 | 513 numeric entries; overwrite every fourth key with `i + 1,000,000` | Small cached filtering traversal that executes checkpoint replay; replay/captured-reader overhead can be a larger fraction than at 100,000 entries |
| F100k | Fork P; overwrite every sixteenth key with `i + 1,000,000` | Large live filtering path, without longer insertion history |
| D100k | Separate fork of P; delete indices 0 through 87,499 | Long deleted prefix: first yield requires filtering and replay; 12,500 live entries remain |
| O32k | 32,768 stable entries, `json()` values `{id:i, group:i%32, active:true}` | Object decoding/GC cost during traversal |

Build P once, then derive F100k and D100k independently from P. Construct E0, F128, F513 and O32k in four separate default arenas. There are **227,320 public writes/deletes per subject process**: 100,000 + 6,250 + 87,500 + 0 + 128 + 32 + 513 + 129 + 32,768. Retain these seven final roots only. No map rebuilding inside iteration samples and no history array of intermediate roots. F128 and F513 answer distinct questions: unchanged-path overhead below the threshold, and replay overhead above it with the entire small key set cached. Correctness coverage at the boundary does not answer that latency question.

Use one consistent attached-reader setup: public `getWorkerData(sevenRoots, {copy:false})`, followed by `initWorker` in the same process, outside all timings. Require genuine shared-memory descriptors, read-only attached snapshots and five unique backing memories; reject a copy fallback. Drop construction inputs and owner handles. Library-owned default-arena references remain ordinary library behavior, identical in both arms. No actual-worker, transport-mode or owner/reader matrix is added; correctness already covers real worker suspension. Record unique current capacities, descriptor used bytes and fixture metadata before and after the experiment. Check complete count/order/value output against a simple independently generated oracle outside timing; compare streaming checksums during timing. P/F/D keep their exact respective roots and log history in both arms.

The object case does not imply uniformly cold or warm decoding. Current main caches at most 2,048 decoded objects and keys. Two initial full traversals establish the ordinary cache state, leaving at least 30,720 object values to decode on each later complete traversal. No private cache clearing or nested-collection claim is made. All seven cases use `entries`; wrapper/projection correctness is already covered separately.

## What to measure

### Paused-iterator memory, P only

Use **one live iterator**, paused immediately after its first successful `next()`, with no retained output collection. Pre-touch its first key/value twice and close those iterators. Preallocate small numeric measurement records; do not log, stringify results or retain memory-API result objects between barriers.

Run two identical cycles per process:

1. No iterator: four event-loop-separated synchronous GC passes, then record the before state.
2. Create one iterator and advance once; validate/discard the yielded pair, retain the iterator, perform the same four GC passes and record the paused state. A subsequent real `next()` must still use this retained iterator, so resumability is observable.
3. Resume once for verification, call `return()`, remove all iterator/result references, run the same four GC passes and record the released state.

Primary increment is **paused minus before**, retained signed. Released-minus-before is an attribution check, not silently subtracted noise. Average the two cycle increments to obtain one process value; the two cycles are not independent replicates. Require absolute release drift in the primary heap metric to be at most 64 KiB per cycle; otherwise that process's memory attribution is unresolved. Do not force released RSS to return to its old value.

At every state retain all of the following separately:

- Node: `heapUsed`, `heapTotal`, `external`, `arrayBuffers`, current process RSS, terminal process high-water RSS. The primary heap measure is `heapUsed`.
- Bun: `bun:jsc` `heapStats().heapSize`, `heapCapacity`, `extraMemorySize`, plus the `process.memoryUsage()` fields and process RSS. The primary measure is **JSC retained heap including owned out-of-heap contents**, not a Node-equivalent object-only heap. `extraMemorySize` is already included in `heapSize`; never add them. Bun's `arrayBuffers` counter is incomplete for some typed-array allocations, as its pinned source explicitly documents.
- Unique arena **used bytes** and **current buffer capacity**, each counted once. Neither configured maximum capacity nor virtual reservation is used memory. No arena growth or write is allowed during measured iteration.

Do not add `arrayBuffers` to `external`, or add either to Bun `heapSize`. The screen compares within-engine paused increments and presents every bucket and RSS alongside them. It does **not** synthesize a cross-engine “total memory” figure. A heap reduction offset by another bucket is a tradeoff. Lower paused retained heap is not lower total process RAM; unresolved RSS stays unresolved. The source model predicts 646 numeric work slots rather than 100,000 for P, but slot counts are **not measured bytes**. Complete P traversal adds 199,290 uint32 loads; this is also a source calculation, not a speed prediction.

### Latency, all seven cases

- **First `next()` on P, F100k, D100k and O32k**: create the generator before its clock bracket; time exactly its first `next()` through the yielded result. Validate the result and close outside that bracket. Sum K such brackets without retaining earlier iterators. Record empty-bracket overhead independently and never subtract it. Mark this endpoint unresolved if overhead is over 0.5% of the observed per-call time, or the clock-resolution rule below fails. No special timer framework or runtime instrumentation is needed.
- **E0/F128/F513 first-item-and-close cycle**: one aggregate bracket around K repetitions of `entries()`, first `next()` and `return()`, with a scalar result checksum (`done:true` for E0; the expected first key/value for F128/F513). This is explicitly a lifecycle endpoint, not isolated first-next latency. It resolves routing costs without per-call clocks. No skipped or special-cased baseline path.
- **Complete traversal**: one bracket around K ordinary `entries()` traversals to exhaustion, with a minimal identical checksum consumer. E0 uses the same `for...of` loop and must yield zero entries. For E0, both endpoints execute one terminal `next()`; the first-item cycle additionally calls `return()` and uses manual advancement, while full traversal measures the ordinary loop. For F128/F513, the cycle closes after one entry, while full traversal yields all 128/513. Treat the paired endpoints as correlated controls, not independent replications or two separate gains. Do not spread to an array or retain decoded objects. Report time per traversal and yielded count; the deletion case is not renormalized to disguise its log scan.

Use `performance.now()` in both engines, verified monotonic and nonzero-resolution in the runtime probe. **Clock-resolution rule:** for every warm-up and measured chunk in both arms, and each of the three baseline verification chunks, measured clock resolution must be **at most 0.5% of the relevant duration**. For isolated first-`next()` endpoints only, the relevant duration is accumulated chunk duration divided by K; for every batched endpoint it is the aggregate chunk duration, without division by K. Zero resolution or zero duration is invalid. Failure in any applicable chunk makes that endpoint unresolved; retain all samples and do not resample. The separate empty-bracket-overhead rule above remains unchanged. Timings exclude fixture construction, attachment, explicit GC, memory sampling, full oracle validation and output; the small streaming checksums are included equally. Their wall costs remain charged to the budgets below. Natural GC during timed work stays in the sample. After the memory phase, run two full validation/cache-establishing traversals per case, then exactly four warm-up chunks and six measured chunks per endpoint. One process contributes the **arithmetic mean of all six measured chunk means**. Slow and GC-affected chunks retain their full weight. No trimming, best-of selection, CV/drift exclusion, extension, resampling or candidate-dependent K.

**Untested latency scope:** process startup, module import/initialization, descriptor creation and attachment latency are outside this narrow screen. Their wall costs are charged to setup and the whole budget, but no endpoint, repetition or clearance claim is added for them. Neither a promising temporary-heap lead nor clearance of all 28 iteration controls establishes latency safety for these operations.

## Fixed run, calibration and resource envelope

**36 child processes total**, strictly one subject at a time:

- Two instrumentation/accounting probes, one per engine, **15 seconds each**. No library import: verify GC/memory/timer APIs and their numeric fields. With four GC passes at each state, separately retain/touch/release an 8 MiB explicit ArrayBuffer, an 8 MiB typed array without exposing `.buffer`, an 8 MiB shared WASM memory, and a 131,072-element array of small objects. Record bucket responses and release behavior. API failure or unaccountable primary heap behavior ends the study as incomplete; never substitute zeros or assume Node accounting applies to Bun. Node uses `--expose-gc`/`globalThis.gc()`; Bun uses `Bun.gc(true)`. These APIs have official source support, but this host has not been probed.
- Two baseline-only calibration processes, one per engine, **90 seconds each**. Build the exact seven fixtures, validate and establish caches. Per endpoint use the fixed K ladder **1, 4, 16, 64, 256, 1,024, 4,096, 16,384, 65,536**; E0/F128/F513 have two additional fixed rungs, **262,144 and 1,048,576**, to resolve their aggregate small-case operations. Select the first chunk with at least 20 ms of accumulated timed duration, or the last K if none does. Then record three verification chunks at that K. Freeze that K for both arms on that engine. A verification arithmetic mean below 5 ms, failure of the clock-resolution rule in any of the three verification chunks, excessive bracket overhead or exhausted calibration allowance makes the endpoint unresolved; there is no second calibration. Calibration has 20 seconds for setup, 60 seconds for all endpoint work, and 10 seconds for records/exit. Non-noise failures stop the study.
- **Eight adjacent baseline/candidate process pairs per engine**: 2 engines × 8 pairs × 2 arms = **32 comparison children**, at **60 seconds each**. Each child contains all seven cases and two P memory cycles. Alternate AB/BA by pair; alternate which engine goes first by pair. Within each pair, both arms use the same case order, rotated by pair index. Alternate first-next/full order by pair as well. Memory precedes all latency in every child. Run no competing subject or benchmark work.

Each 60-second child has phase ceilings of 20 seconds setup/fixtures, 8 seconds memory, 22 seconds fixed warm-up plus latency, 5 seconds final checks/output and 5 seconds owned exit/cleanup. All validation and GC are included. There are **2,688 measured timing chunks**, **1,792 fixed warm-up chunks**, **64 memory cycles**, and at most **192 memory-state barriers / 768 GC passes** in comparison children. Calibration/probe GC and initial validation traversals are additional explicitly budgeted work, not statistical samples.

Whole prospective wall ceiling: **120 staging/pin seconds + 2×15 probes + 2×90 calibration + 32×60 comparison + 90 analysis/sealing + 60 final cleanup = 2,400 seconds (40 minutes)**. These are ceilings, not target duration. Setup uses already prepared authenticated runtimes; missing artifacts or required new builds/installations require a separate reviewed plan. The controller owns every child process group, enforces both phase and whole deadlines, preserves the first failure and stops without retry. Late child output cannot restore eligibility. Receipt/hash generation and killed-child cleanup consume the remaining whole budget.

The long ceiling comes from giving every fresh process bounded construction, GC and cleanup headroom, not from requesting 40 minutes of timing. Nominal comparison timer exposure at the 20 ms target is **32 × 14 × (4+6) × 0.020 = 89.6 seconds**, before variability; K is fixed from baseline, so candidate exposure can differ. Adding F513 contributes **12.8 seconds nominal exposure** across comparison children, plus its fixed baseline calibration and validation, all inside the unchanged ceilings. Wall time also includes 34 fixture constructions (7,728,880 public updates), validation, GC, closure work, imports and control overhead. **Expected wall time is not empirically established**; the two fixed calibrations will report observed setup and batch costs without adding a pilot or changing this protocol. Given the ceiling and previously observed local executor loss, durable hosted execution is preferable to a long local attempt. No hosted packet, publication or run is authorized by this proposal.

Use a quiet dedicated Linux host with at least **4 GiB available inside its effective container/host limit** before launch. Enforce a **2 GiB sampled process-group RSS stop**, including setup; admit measured work only if post-fixture RSS is at most **1 GiB** and total unique arena capacity is at most **512 MiB**. This leaves 1 GiB child headroom rather than treating a construction peak as the measurement limit. Poll RSS every 50 ms outside the subject, retain terminal high-water data, and label sampled maxima honestly; they are not hard peak bounds. Do not change Node heap flags or Bun GC tuning between arms. A resource failure is incomplete evidence, not a demonstrated algorithmic regression or permission to shrink fixtures/increase limits and rerun.

## Decision rules fixed before execution

The independent unit is the **process pair**, n=8 per engine. Retain every raw sample. For each latency endpoint form the same eight paired log(candidate/baseline) ratios of process arithmetic means and report their geometric mean with **both an ordinary two-sided 95% paired Student-t interval and a 95% Bonferroni simultaneous interval across all 28 engine × case × endpoint comparisons**. The ordinary interval detects harm; the simultaneous interval governs clearance. This is a small-sample model-based screen: disclose that assumption. Show chunk distributions and leave-one-pair-out sensitivity alongside the fixed full-sample result. Natural GC, wide variation, order effects and that sensitivity remain diagnostics; they cannot selectively invalidate or exclude an otherwise valid adverse result. No post hoc subset, replacement process, sample extension or interval selection is allowed. Wider uncertainty from allocation/GC variability must remain visible; do not import read-only CV/stability rejection rules.

- Any valid latency endpoint whose **ordinary two-sided 95% interval lower bound exceeds 1.02** is a material adverse control and **vetoes a promising lead and blocks promotion/further performance validation of this unchanged candidate**, regardless of memory benefit. This veto applies even if its wider Bonferroni interval overlaps 1.02 or other endpoints are unresolved. The pointwise harm veto is intentionally conservative about advancing the candidate: unlike simultaneous clearance, it does not provide 95% family error control across the 28 opportunities to stop. Preserve independently valid demonstrated >2% harm from any other authorized measurement; this screen cannot waive it.
- A control is cleared only when its valid **Bonferroni simultaneous upper bound is at or below 1.02**. A valid result satisfying neither the pointwise harm rule nor simultaneous clearance is unresolved, never “no regression.” Predeclared measurement failures, including missing pairs, inadequate clock resolution/bracket overhead, failed identity/oracle checks or process/resource limits, remain unresolved/incomplete under the existing rules. All valid slow/GC samples stay in the full-sample result. Do not pool engines or average a slowdown away.
- For P memory, use paired arithmetic contrasts with Student-t uncertainty and **95% Bonferroni simultaneous intervals across ten contrasts**: five per engine. The lower bound on baseline paused heap increment must exceed **512 KiB**; the lower bound on baseline-minus-candidate saving must exceed **256 KiB**; the lower bound on `0.5×baseline − candidate` must exceed zero. Upper bounds on candidate-minus-baseline paused `external` and `arrayBuffers` increments must each be at most **64 KiB**; the two diagnostic guards are not added as bytes. Arena used/capacity must be exactly unchanged through iteration. Failed attribution/accounting makes memory unresolved, not zero.
- **Promising temporary-heap lead** requires those P memory conditions on both engines and no valid adverse latency control. If latency controls are unresolved, this outcome permits only a separately proposed targeted validation; it cannot support promotion or a regression-free claim. A meaningful memory result never waives an actual >2% slowdown. If all controls clear, report that narrow screen result, still subject to later independent review and ordinary correctness.
- If a valid memory interval rules out either required absolute or fractional materiality on either engine, reject the cross-engine benefit hypothesis. Otherwise unresolved memory is inconclusive. No extra samples are authorized by either result.

Report same-scenario paused/current RSS and process high-water RSS with uncertainty as diagnostics. Any confident adverse RSS movement or unexplained bucket shift must be explained before calling the lead useful. Do not claim a total-RAM saving without a separately supported RSS result; even a favorable RSS result here describes this forced-GC, single-process scenario only.

Their states are retained collections, not a paused ordered iterator. The separate `docs/memory-comparison.md` worker chart uses **SharedList** columns through `website/assets/explorer-storage.mjs`. The old empty-prefix runs remain parked with zero comparative samples.
