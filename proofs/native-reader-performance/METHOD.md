# Native-reader session performance screen

Prospective method v2, 2026-10-16. **Source only: no driver, calibration, or performance execution accompanies this document.** Timing admission requires successful terminal correctness evidence and an independent audit for the exact candidate below. A source review alone is insufficient.

## Question and fixed implementation

Does sharing pure native reader exports improve real later shared-session publications, including a small application read, in Node.js 22.16.0 and Bun 1.4.2? The candidate still constructs new JavaScript Arena state, registries and view-local caches. It lazily creates a view's own mutable native instance when necessary. It does not share decoded values. This screen tests session publication/acceptance and application completion, not isolated object decoding, universal regression freedom, or browser performance.

## Two fixtures, seven workload rows

Use only public collection and session APIs. Every timing process has one real `node:worker_threads` worker; verify that route under both engines before measurement. No mock endpoint, direct private attachment call, replayed synthetic protocol frame, or direct Arena construction stands in for a session publication. Explicitly set `copy: false` except in C8, `delivery: 'all'`, `maxPending: 1`, and `timeoutMs: 10000`. Publish sequentially after the previous application response and session acknowledgement. Never rely on the Bun copy default.

Each map contains 128 keys, in ascending construction order: `k` plus the zero-padded four-digit index `i`. P1 uses `SharedMap('number')`: V0 has value `i`, and V1 changes only `k0000` to `100000`. P8 uses `SharedMap('object')` for each map `j=0…7`. Its V0 values are small catalog records with exactly these own fields in insertion order: `{ id: 128*j+i, price: 100+10*j+i/4, active: (i+j)%2===0 }`. P8's V1 changes only the record at `m0.k0000`, increasing its `price` from 100 to 101 while keeping `id` and `active` unchanged. Prices are exact binary64 quarter units; no decimal-rounding tolerance is needed.

Build both immutable versions once. Use public `resetMap()` before each independent map's construction to give it a separate arena. Retain both versions; perform no collection writes or memory growth during repeated timing. For the eight-map record, use keys `m0` through `m7` in that order. Exactly eight independent arenas must be confirmed from public `getWorkerData`, not assumed from wrapper count. R8 uses the complete P8 V0 payload; C8 uses the same alternating P8 object records; W8 reads the retained final P8 view.

P1 alternates its two versions. P8 alternates records differing only in `m0`; `m1`–`m7` are the identical original handles. These are genuine changed descriptors on already-known Memory objects. The efficient baseline is unchanged: P8 still reconstructs all incoming arenas and calls its normal factories before retaining seven unchanged top-level handles. Do not force those seven handles to change to improve the candidate's ratio.

F8 also uses object maps: for group `g=0` or `g=1`, record fields in the same order are `{ id: 1024*g+128*j+i, price: 1000*g+100+10*j+i/4, active: (i+j)%2===0 }`. Group 0 has the P8 V0 values but uses its own eight arenas; group 1 has another eight disjoint arenas. Neither F8 group uses the P8 V1 price adjustment. Alternation removes then reintroduces each group; the prior active wire set contains none of the next group's arenas. Confirm each frame carries all eight Memory handles and uses eager attachment. This isolates attachment fallback without charging unrelated writer reconstruction inside the timer.

The reader query makes 16 `get` calls per map, in order, at indexes `(17*q)%128` for `q=0…15`. P1 sums the numeric values; P8/R8/C8/F8/W8 sum each returned object's numeric `price`. It includes the changed key and consumes the results. Thus P1 reads 16 numeric values and each eight-map query reads 128 objects. Record this application-work difference; do not normalize P8 as if it were eight independent session requests. Object decoding tests whether attachment savings survive a small catalog query. Both arms retain their own fresh per-view decoded caches: no decoded-cache sharing is introduced.

The independent oracle constructs expected fields directly from the formulas above. The queried indexes sum to 1016. P1's exact query totals are 1016 for V0 and 101016 for V1. P8/C8 totals are 19312 for V0 and 19313 for V1; R8 is always 19312; W8 uses its retained view's declared version. F8 totals are 19312 for group 0 and 147312 for group 1. Derive object totals independently by summing integer quarter-price units (`4*price`) and dividing by four. For an alternating batch, sum the appropriate per-publication totals using its recorded starting version/group and operation count; do not infer expected values from either arm's outputs. All accumulated query checksums remain exactly representable numbers under the fixed count caps.

Fixed row order is P8, P1, N8, R8, C8, F8, W8. Allocate all source fixtures and prepare query keys outside repeated timers. Permit at most 32 owned source arenas, 8 MiB total committed source buffers and 1 MiB per arena; otherwise stop. Retain at most the initial, preceding and current reader snapshot for each active row, and only the latest R8 result. Keep the P8 reader/session only until its N8 and W8 controls finish; dispose other row readers/sessions when finished. Keep no publication history. Retain scalar timing/checksum aggregates, not every generated view.

## What is timed

For P1/P8/C8/F8, the primary operation is owner `publish(next)` through receipt of the worker's small application response after its fixed query. The timed batch is a fixed-count sequential loop and includes capture, publication, structured messaging, receiver attachment, query, acknowledgement handling, harness Promises and checksum consumption. It excludes source construction, imports, assertions and row teardown. There is no empty-loop, message, or clock subtraction.

A transparent endpoint adapter forwards the unmodified real worker event to the library listener. It records the worker-local monotonic timestamp immediately before dispatch of a snapshot event. The application subscription records acceptance at entry, then query completion. Report summed dispatch-to-subscription latency and summed query latency per publication separately. The former includes protocol validation, the promise chain, native attachment, factories and acceptance dispatch; label it **receiver acceptance**, not isolated native-instantiation time. All clock differences are within one thread. Do not subtract sender and worker clocks or add overlapping components into an invented total.

The subscription queues the application response in a microtask, so the library's synchronous post-subscription acknowledgement precedes it on the same port. The adapter verifies sequence/count ordering outside the measured batch. Wait for both acknowledgements before advancing if the implementation cannot establish that ordering. Any extra wait stays in the declared end-to-end estimand in every arm. An end-to-end batch uses two owner clock reads; receiver component clocks and fixed response instrumentation are identical in all arms and included in the measured workload.

R8 and W8 run their fixed-count loops in the worker, with two worker clock reads per batch. R8 includes awaiting `initWorker` and querying each new result; payload preparation and command transport are excluded. N8 has an owner-local batch timer. Do not call N8 a network round trip or a successful native-reuse hit.

Each fresh process imports shared-then-worker in its owner, records first creation, builds fixtures, then starts its worker. The worker imports shared-then-worker before connecting P8. Keep this order identical in every arm. Every fresh measurement process records these **single cold events**, before any warm-ups:

1. Dynamic import of both public portable entry points in the fresh worker realm, in fixed shared-then-worker order. Include module parsing/evaluation and native module construction, including any compilation the runtime performs; do not pre-import a subject in the harness.
2. First owner `new SharedMap('number').set('cold', 1)` immediately after its imports and before fixture construction.
3. Initial eight-arena session creation/connect through reader-ready application response, with the fixture already built. Record worker dispatch-to-connect-promise resolution separately; this initial boundary differs from a later subscription.
4. The first changed P8 publication through application response, with receiver acceptance/query components. This must be the worker realm's first eligible reuse, before creating any other session. It includes the candidate's one-time export-descriptor/WeakMap initialization.

Keep cold events separate from steady-state estimates; do not average first reuse into warmed publications or warm it away. Fresh processes/worker realms provide fresh JavaScript/module/native state, not a promise of cold OS file caches. Record worker creation-to-ready and complete process wall time as setup evidence, without treating setup as free or subtracting it from results. Single cold events have 12 independent block replicates per arm/engine and can remain unresolved because of noise.

## Replication, counts and feasibility

Use 12 paired blocks per engine. Each block has independent fresh B (baseline), C (candidate) and A (second baseline) processes. A imports the identical baseline artifact, with its own complete setup and observations. Repeat the six process orders twice: `B C A`, `A B C`, `C A B`, `B A C`, `C B A`, `A C B`. Run Node first in odd blocks and Bun first in even blocks. Run only one process/worker group at a time on one hosted Linux x64 machine, with no concurrent build/test/study work. Keep runtime flags and environment identical. Record CPU/OS/container limits and affinity, runtime identities, order and timestamps; do not tune GC or apply explicit GC.

One baseline-only calibration process per engine chooses counts before candidate timing. Start at 32 operations for P1/P8/R8/C8/F8, 256 for N8 and 128 for W8. Each of at most three trials has two discarded warm-up batches and three pilot batches. Accept median main-endpoint duration **40–80 ms**, targeting **50 ms**; otherwise multiply count by `50 ms / median`, round to nearest positive integer and clamp to the fixed cap. Caps: 8,192 for publication/attachment rows, 2^20 for N8, 2^18 for W8. Reject nonpositive/nonfinite time. No candidate calibration, fixture resizing or component-specific count tuning. Freeze the final actually attempted count per engine/row for B/C/A; never freeze an untried extrapolation. Failure of either primary to reach the calibration window aborts measurement admission. A control that merely misses the window retains its final actually attempted finite count, stays unresolved, and proceeds to the prescribed full rehearsal.

Then run one **fresh baseline-only full rehearsal per engine**, with the exact measurement lifecycle: imports, worker startup, cold events, fixture setup, all rows, all validations, output, disposal and worker termination. It has three discarded warm-ups and seven measured batches per row, exactly as each measurement process will. This rehearsal provides no efficacy evidence. Record elapsed cost by phase and total supervisor-observed lifetime, including polling/reaping. Admission requires `2 × 36 × (T_Node + T_Bun) + 30 seconds` to fit the remaining study budget, where each T is that engine's entire rehearsal lifetime. The fixed factor of two reserves variation and candidate overhead; it is not a guarantee. Do not substitute a timed-batch-only projection. Primary calibration failure, an invalid time/count, a cap/resource failure, or failed rehearsal/projection stops admission as incomplete. A control merely missing the 40–80 ms calibration window is the stated exception: keep its final tried count, label it unresolved, and proceed to rehearsal. Do not shrink rows, omit validation, change sample counts or extend caps to make it fit.

The complete screen comprises **80 experimental process groups**: four mechanism preflights, two calibration, two rehearsal and `12 × 2 × 3 = 72` measurement processes. Each group starts exactly one worker. There are no replacement, extra warm-up, validation-only or retry groups beyond these. The 72 measurement groups run `72 × 7 × 10 = 5,040` timed batches. At 50 ms this is 252 seconds of main-endpoint work alone; the rehearsal, not this arithmetic, determines whether complete execution is feasible.

## Fixed inference and decision

For each engine/row, take each process's arithmetic mean of seven elapsed-per-operation batch values. The independent unit is the block, **n=12**, not a batch or publication. Calculate `d = log(C/B)`, `R = exp(mean(d))`, and the ordinary two-sided 95% paired Student-t interval `exp(mean(d) ± 2.200985160 × sampleSD(d)/sqrt(12))`, df=11. Apply the same method to each cold event and reported receiver/query component. Report A/B and chronological later-baseline/earlier-baseline intervals separately; never average A with B, relabel B after seeing results, pool engines or use rehearsal/calibration observations as replicates.

For repeated rows, a process/endpoint is quality-qualified only when every measured batch is finite/positive and **each measured batch's aggregate elapsed duration, before dividing by its operation count, is at least 20 ms**. The floor never applies to the sum of seven batches. Its seven-batch sample CV must be at most 20%, and its last-three/first-three mean ratio must be in [0.90,1.10]. For a receiver component, apply the 20 ms floor to the sum of that component's per-publication durations **within each measured batch**, independently; short components remain descriptive/unresolved even when end-to-end qualifies. Cold events are not subject to a fictitious batch-duration target: require all values finite/positive, within-arm block CV at most 25%, and last-six/first-six mean ratio in [0.90,1.10] for provisional clearance. Keep all observations in the full-sample analysis; quality failures never justify deletion.

An A/B or chronological-baseline 95% interval entirely above 1.02 or below 0.98 blocks favorable inference for that engine/endpoint. The same bias on N8 blocks both primary claims in that engine. Otherwise a wide A/A interval is not proof of stability or equivalence. These small-sample intervals depend on approximately independent, reasonably behaved block log ratios and cannot eliminate shared-host confounding.

**A promising scoped lead requires the same primary (P1 or P8) to have an end-to-end interval upper bound ≤0.95 in both engines**, with complete source/value/admission evidence, that primary calibrated and all its B/C/A end-to-end process observations quality-qualified in both engines, and no blocking A/A bias. The two choices are predeclared. Each displayed upper bound is also a 97.5% one-sided bound; allocating one-sided alpha 0.025 to each primary and requiring both engines for that primary gives an intersection-union test with Bonferroni control across the two choices at 0.05 under the stated model. A Node P1 win and a Bun P8 win do not qualify together. A receiver-only improvement cannot rescue a failed end-to-end primary.

**Any source-authenticated, value-valid endpoint with a computable full-sample 95% lower bound >1.02 in either engine vetoes this unchanged candidate**, including the other primary, cold events, all controls and components. Apply this adverse-evidence rule even when short batches, calibration, CV, drift or A/A flags prevent favorable interpretation; retain and explain those limitations. It is a deliberately conservative stop rule, not simultaneous proof of harm. Wrong-source/value data cannot establish candidate latency; missing/nonfinite observations remain incomplete. A separately valid adverse finding stays visible if another failure makes the study incomplete.

A control is provisionally clear only if all its calibration/quality/bias prerequisites hold and its interval upper bound is ≤1.02. All other non-veto outcomes are **unresolved**, including noisy cold controls. A qualified primary with unresolved controls supports only a promising result for the named session workload and further targeted validation; it does not establish general no-regression or release readiness. No qualifying primary or an incomplete screen yields no lead. No resampling, outlier trimming, replacement children, threshold movement or post-result workload selection is permitted.
