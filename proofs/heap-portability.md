# Heap-entry portability diagnostic, prospective attempt 1

This frozen plan selects exactly three original cases on five new lanes. It is a portability diagnostic, not a rerun or replacement of the original x64 campaign. There are no results from this plan yet. Preparation permits deterministic fixtures and untimed checks only. Publishing this proof, starting a CI run, changing PR25, or collecting local latency is not authorized by this document.

## Untimed semantic barrier

Before any pilot, each lane verifies both arms for the three selected fixture outputs, descriptors, copied source byte hashes and capacities. Four additional fresh subjects, baseline/candidate × shared/copied transport, each create one actual worker. Each checks empty numeric, 33-number, 65-nested, 1,057-number, and 4,097-string heaps. This is 10 correctness subjects, four real workers and 20 worker rows per lane.

The semantic checks reuse the original proof's generator shape, lazy access, binary64, decoder receiver/order/reentrant growth/exception, storage and worker handlers. They verify no view access on generator creation or return/throw before first next, empty completion, interleaved iteration, early close/throw, source bytes/state/descriptors, actual shared markers versus copied isolation, writer growth before first next and while workers are paused, read-only mutation rejection, and the expected three-view-request reduction per visited entry. Baseline/candidate outputs and byte/state records must agree. These probes never run inside timing subjects.

Browser workers use the original portable public entry through the existing structured worker protocol. The transport is derived from the reviewed radix recovery candidate `7fe90c039ef6fdfa3f1bac85655df7b9979ab63c`, tree `b3fa6631efbec2f926b153ca69ff837262622285`. The retained Chromium artifact from published recovery `8b8e6d78ee444ce07b1ee59a652106e0221c7a69`, run `37882888216`, matches the lifecycle, process, shim, browser and adapter files byte-for-byte to that review tree. This verifies source reuse, not heap browser execution. The exact worker close promise is installed at worker registration before page navigation. The expected worker count and every exact close must be observed before browser teardown, within 30 seconds. Browser closure, disconnection, server closure and outer process-group cleanup remain independently required. A late close during teardown cannot change a failed barrier to success. The lifecycle helper is copied unchanged and hash-bound. Server-close or final source-check failures preserve the subject's already returned partial result while marking cleanup failed.

No full test suite or browser is run during local preparation. Future CI builds only the pinned WASM and portable bundles and runs the focused semantic barrier. Historical full suites and PR25's normal CI remain separate evidence.

## Calibration, replication and fixed work

Original heap calibration is retained: the initial repeat is `max(1, floor(4096 / max(1, size)))`; pilot prewarm runs that fixed batch size toward 500 ms with the original 10-second cap. Calibration takes three samples per step, uses the fastest, and targets at least 50 ms (40 ms plus 25%). Its original growth factor, maximum 16 steps, 10,000,000-repeat limit and cap flags remain intact.

The browser adapter explicitly starts calibration from the last positive recorded prewarm batch's repeat. In this original heap prewarm every batch has the same repeat, so this does not change the count or introduce radix's calibration algorithm. Unlike the original radix pilot, the heap pilot has no restart-to-one assignment or per-probe positive-duration assertion. A zero clock-quantized probe remains visible and follows the original bounded escalation; it is not replaced or presented as a positive observation. No zero-duration guard is weakened. Missing positive prewarm evidence fails. Deterministic fake-clock checks establish this difference; they are not latency evidence.

All six pilots in a lane finish before any of that lane's measured subjects. The common repeat is the maximum arm pilot repeat. The common warmup count uses the fastest pilot milliseconds per consumption, the original 25% cushion, and whole-batch rounding. The original `freezePlan` function is copied unchanged. Every AB and AA subject uses those same fixed warmup and measured counts. The 500 ms warmup and 40 ms batch targets remain visible; original validity floors are 150 ms and 10 ms. Measured work is never extended for one arm to reach a clock target. Caps, short work and floor misses invalidate rather than cause retries.

For each lane/case, four AB and four baseline-AA quartets comprise two LRRL and two RLLR orientations each, with original seeded shuffle/mode ordering. Each subject is a fresh process; browser subjects additionally launch a fresh default browser. Left is baseline; right is candidate for AB and baseline for AA. Both arms run at one identical neutral filesystem path and, for browser code, one identical origin/path. Controller-only build labels are excluded from timing requests. The full neutral package and helpers are verified before and after each subject; all previously copied chunks are removed between subjects.

Each measured subject performs 21 batches. One adjacent pair log ratio uses process-median milliseconds per public consumption. Two pair logs average into one quartet effect. The four quartet effects, not batches or eight pairs, give the original pointwise two-sided 95% Student-t interval, df=3, t=3.182446305284263. AA drift is a geometric ratio outside `[1/1.02, 1.02]` whose interval excludes 1. It invalidates matched AB; AB is never divided by AA. A usable AB lower bound above 1.02 is a material loss; an upper bound below 0.98 establishes a selected-cell gain. There is no simultaneous multiple-comparison guarantee and no cross-engine pooled speedup.

Per lane: 3 cells, 6 pilots, 96 measured subjects, 24 quartets and 2,016 measured batches. Across five lanes: 15 cells, 30 pilots, 480 measured subjects, 120 quartets and 10,080 measured batches, plus 50 correctness subjects and 20 workers. That totals 560 fresh subject processes plus 20 build command groups. The three browser lanes additionally require 336 fresh-browser lifecycles. All results, including incomplete/invalid/inconclusive cases, stay visible. Even every selected interval within margin produces only `selected-cells-within-margin-only`.

## Failure handling, evidence and runtime budget

Every external child has an owned process group, immediate command/start receipt, separate raw stdout/stderr, fixed deadline and verified cleanup. No later child runs after unverified cleanup. The controller retains all completed correctness/pilot/measurement records, source and derived helper bytes, common plans, manifests, schedule, hardware context, browser network source receipts and terminal errors. Reversible subject observation hooks retain the current warmup/calibration/measurement arrays when a normal subject exception occurs; the scan and sink timer body stays unchanged. If the process is killed before returning JSON, its raw logs and all earlier subjects survive; unreturned in-memory samples are not claimed recoverable.

No timing-driven retries, added quartets, outlier deletion, case omission, tuning or reruns are allowed. Every lane has a 25-minute controller budget, 27-minute controller step and 55-minute job envelope, giving an upper envelope of 275 aggregate job-minutes across five jobs; setup/browser install are bounded separately within those job envelopes. Every completed or partial evidence directory is packaged in an external tar.gz with SHA-256 under an always-run step and uploaded under a lane-specific name. There is no dispatch trigger. A future authorized single nonforced push must be a direct child of the exact PR25 head on `proof/heap-entry-portability-20261009`, with event-before equal to that head and run attempt 1. Creating the branch at the head is not itself a timing trigger because branch-creation events fail the guard.

Budget estimate, not a new measurement: the same three original x64 cases used 280.5 seconds of Node pilot+measurement process time and 236.3 seconds of Bun process time. ARM64 may differ. Browser launch/teardown adds 112 fresh-browser lifecycles per engine, 336 across the three browser lanes. Provision approximately 6–12 minutes per ARM lane and 10–20 minutes per browser lane after dependencies, subject to the 25-minute hard controller limit. Five parallel lanes would ordinarily complete within roughly 15–30 minutes including setup; 45–90 aggregate runner minutes is an estimate, not the 275 aggregate job-minute upper envelope. Queue delay, browser installation and calibration caps can prevent completion; no automatic extension or replacement is permitted.
