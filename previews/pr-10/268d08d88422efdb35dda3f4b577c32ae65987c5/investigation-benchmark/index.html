ONE WORKLOAD. THREE ARCHITECTURES.

Measure the trade-off.

Search, summarize, and read a page of events. Then append a batch and do it again. Compare shared snapshots with two credible native-data designs.

Checking shared-memory support…

On hosts without isolation headers, this installs a same-origin service worker for this demo path, then reloads once. It does not cache requests. The rest of the docs work without it.

Uses CPU and memory. Keep this tab visible. Two warm-ups and seven measured samples per path. No data leaves this browser.

Shared snapshots

One owner. Two readers attach shared columns. The UI reads visible rows directly.

Native replicas

Two workers keep native arrays. Copy the initial columns once; send only appended events on update.

One data owner

A single worker owns native arrays, performs both calculations, and returns the first page of rows.

What each phase means

Initial sharing

Send the existing input and await attachment in all readers. Native data is structured-cloned. Shared view creation is included. No query in this phase.

Query an attached dataset

Run the same search and summary. Include worker messages and the first 50 materialized rows. Do not resend the dataset. Both scans yield periodically to keep cancellation possible.

Append, publish, query

Append 2,000 events, synchronize readers, and repeat the query. Native replicas receive only the delta—not another full copy. Shared immutable appends and attachment are timed.

Boundaries and fairness

A coordinator stands in for the UI, so timings exclude DOM rendering, user input, startup, and module loading. Construction is separate. Paths rotate. Each answer is checked against an independent native-array reference outside timing.

No universal winner is expected. For append-only data, native readers can also retain an earlier view by length. This workload does not prove a unique snapshot benefit. It does not measure process memory, arbitrary edits, SQL, or end-to-end UI latency.
