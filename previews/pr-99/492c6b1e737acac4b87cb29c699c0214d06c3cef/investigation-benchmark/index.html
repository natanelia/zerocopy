Checking the source build metadata…

Two warm-ups and seven measured samples per case. All workloads run in one action.

Method, timing boundaries & correctness

Four separate questions

  • Full-object .get(): returns ordinary, deeply frozen records. The cold query is the first access in a fresh reader; the repeat query immediately requests the same IDs. No validation pass runs between them.
  • Selective query: find available books and return ID, name, price and revision. Native Map, Immutable.js, Immer, ZeroCopy .get() and ZeroCopy getView() return the same ordered result. No full-record fingerprint is computed.
  • Construction through first answer: construction + initial publication + first worker request/reply. Each sample is added before calculating its median. Parallel reader times are never added as serial work. Worker startup, module import/compile, fixture generation and reference checks are outside this total.
  • Legacy catalog control: the original lookup and validation tasks, including full-record fingerprint generation inside the query timer and worker response transport. Only the independent reference comparison is after timing.

Equal work and retained revisions

Each sample starts with fresh owner and reader workers. Two readers receive the same 1,000 requested IDs: 910 hits and 90 misses. New workloads capture all result rows and compare every value, count, miss and position against an independent reference after the first query and repeat query have both finished. After replacing 100 records, current revision 1 and retained revision 0 are checked too.

Read bars show local query work: the slower of the two reader durations, with each duration retained in the export. The worker round-trip also includes scheduling, request/reply messages and result transport; those times are reported separately. Replica records are decoded and frozen during attachment. ZeroCopy .get() decodes and freezes records on demand, then can reuse its bounded cache. On edits, each shared reader passes its previous attachment so unchanged JSON records can reuse their frozen values. Native-object creation from getView().toObject() is a separate workload: its default is fresh and mutable, while { freeze: true } is deeply frozen.

Legacy copy strategies remain unchanged

Incremental-copy replicas publish only changed pairs; full-copy replicas publish the entire updated catalog. Only “Publish the edited revision” and “Replace and publish 100 products” add full-copy bars, immediately below SharedMap. Native Map makes one shallow index copy to retain revision 0. SharedMap publishes descriptors to shared memory. Logical record-delivery counts do not measure bytes or heap use.

Reproduce the displayed results

Cases rotate in a fixed order. Every warm-up and measured sample is retained in the versioned JSON export, along with source/build hashes, API and freeze contract, IDs, runtime/browser details, publication counts, timing boundaries and correctness results. An interrupted or failed run exports its partial evidence and failures without publishing incomplete medians. The recorded memory bars stay unchanged.
