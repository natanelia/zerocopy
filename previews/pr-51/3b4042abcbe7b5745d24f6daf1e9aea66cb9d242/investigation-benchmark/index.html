Preparing this demo…

Setup normally runs automatically. This host may need one page refresh to enable shared memory. If your browser blocks service workers or isolation, open this page in a full browser or use a host with COOP/COEP headers. Documentation stays available; there is no copy-mode fallback.

Four cases across all phases; three extra full-copy cases for edited publication · two warm-ups and seven measured samples per case (49 measured samples total). No assumed winner.

What the timers include

Each sample starts with fresh owner and reader workers. Startup and module loading finish before timing. All four baseline cases separately measure input generation, construction, initial publication, reads and updates. Initial publication sends the full catalog to replica readers; SharedMap sends descriptors for shared backing. The first query requests 1,000 IDs once; the repeat query uses the same IDs. SharedMap can cache decoded JSON locally. Full-copy cases load the same data for fairness but record only the two edited-publication timings.

The update replaces 100 objects in every case. Incremental-copy cases publish only changed pairs. Full-copy cases encode and structured-clone the entire current catalog to both readers, including unchanged objects; each reader replaces its current map. Publication includes reader reconstruction or freezing and waits for both acknowledgements. SharedMap publishes shared descriptors. Owner update and publication have separate timers, plus a direct timer for the combined operation.

All workers retain revision 0 and current revision 1. New and retained answers are checked after timing. The owner update is the same for both copy strategies: native Map makes one shallow index copy for this first edit, Immutable.js batches with withMutations, and Immer batches with produce. Local structural sharing and shallow index copies are separate from the dataset copied between workers.

All cases use identical records, IDs, worker counts and validation rules. Cases run in rotating order. Raw JSON includes all 63 records (14 warm-ups and 49 measured samples), explicit measured phases for each case, the copy strategy, source commit and dependency versions. Full-copy samples contain only edited-publication timings, not duplicate baseline phase timings. These timings exclude DOM painting and do not measure memory.

HISTORICAL MEMORY · SYNTHETIC RECORDS

Compare memory with reader workers.

The fixed recording uses 100,000 synthetic objects, 1,000 requested IDs, 100 replacements, and the same retained initial revision in every owner and reader. Each comparison below uses the same number of readers. These recordings use an earlier synthetic-record fixture, not the current product catalog. The live size selector does not change this chart.

Recorded copy strategy: incremental copy. Native Map, Immutable.js Map and Immer Map receive the full dataset at load, then only changed records on edits. These memory figures do not measure full-copy updates.

Recorded runtime baselines: 8ad5788 (two/four readers) and f140ebe (eight readers), with matching library bytes. These figures predate the later main-branch optimizations, including PR30; they do not measure the current live example build.

Both compare medians from three fresh trials with 100,000 synthetic records, 100 replacements and initial/current revisions retained. Retained data and RSS use different accounting; they cannot be added or subtracted to explain the rest of the process. These are endpoint measurements, not peak memory.

Eight readers, recorded separately

The eight-reader run used AMD EPYC 7763 64-Core Processor; the original two/four-reader run used AMD EPYC 9V74 80-Core Processor. Runtime and adapter bytes match, but these are separate cohorts. Compare libraries within each cohort; these panels do not form a controlled same-host scaling curve.
