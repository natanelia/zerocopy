THE GOOD PART

Move the work.
Not the whole dataset.

Search a stream. Inspect a record. Read locally on either thread.

Connect a worker once. A session delivers snapshots. After attachment, .get() is a synchronous local read. It does not ask the main thread for a value.

Understand the model →
Collections hold data. Sessions share snapshots.
Tasks only schedule work.
Main thread · API excerpt
// With your existing state and worker
await state.connect(worker);

// Read directly on the main thread.
state.current.events.get(42);

// New events create a new snapshot.
state.update('events', events =>
  events.push('Upstream timeout')
);
Worker · API excerpt
import { connectSharedSession }
  from 'zerocopy/worker';

const shared = await connectSharedSession<Model>();

// No task. No per-read message.
const snapshot = shared.current;
const event = snapshot.events.get(42);

// This snapshot stays fixed across later updates.

THE RIGHT TOOL, NOT EVERY TOOL

Keep your stack.
Know the trade-offs.

Start with a collection. Bring your existing workers, Redux store, or message protocol. Add a task pool when you need one.

Find your starting point →
Where zerocopy fits

Large, versioned collections that multiple threads need to read. Log explorers, editors, large tables, catalogs, graph tools, and simulations with a changing dataset.

What you need to know

Browsers need cross-origin isolation. Each arena has one allocating writer. Worker snapshots arrive asynchronously. Long-lived data needs an explicit compaction strategy.

Read the memory guide →
When native collections are better

Small data that stays on one thread. Sharing avoids dataset copies; it does not make every collection operation faster or remove all allocations.
