No stored scores. Run it to measure on this device.

Shared snapshots

One owner. Two readers attach shared columns. The UI reads visible rows directly.

Immutable.js Lists

Two workers keep persistent Lists. Batch updates with withMutations. Clone only new column values and rebuild Lists in each reader.

Native replicas

Two workers keep native arrays. Copy the initial columns once; send only appended events on update.

One data owner

A single worker owns native arrays, performs both calculations, and returns the first page of rows.

What each phase means

Initial sharing

Send the existing input and await attachment in all readers. Native data is structured-cloned. Immutable.js includes plain-column encoding, structured clone, and List construction in readers. Shared view creation is included. No query in this phase.

Query an attached dataset

Run the same search and summary. Include worker messages and the first 50 materialized rows. Do not resend the dataset. All paths read collections directly; no List-to-array conversion is used for queries. Both scans yield periodically to keep cancellation possible.

Append, publish, query

Append 2,000 events, synchronize readers, and repeat the query. Both native and Immutable.js replicas receive only the delta—not another full copy. Immutable.js owner updates, delta encoding, and reader List updates are timed. Shared immutable appends and attachment are timed.

Boundaries and fairness

A coordinator stands in for the UI, so timings exclude DOM rendering, user input, startup, and module loading. Construction is separate. Paths rotate. Each answer is checked against an independent native-array reference outside timing.

No universal winner is expected. For append-only data, native readers can also retain an earlier view by length. This workload does not prove a unique snapshot benefit. It does not measure process memory, arbitrary edits, SQL, or end-to-end UI latency.
