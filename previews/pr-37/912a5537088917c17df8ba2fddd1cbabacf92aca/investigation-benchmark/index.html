MEASURE YOUR BROWSER

One product catalog.
Four implementations.

Separate construction, publication, first queries, repeat queries and sparse edits. Every worker answer is checked against an independent reference.

Preparing this demo…

Setup normally runs automatically. This host may need one page refresh to enable shared memory. If your browser blocks service workers or isolation, open this page in a full browser or use a host with COOP/COEP headers. Documentation stays available; there is no copy-mode fallback.

Two warm-ups and seven measured samples per implementation. No assumed winner.

What the timers include

Each sample starts with fresh owner and reader workers. Startup and module loading finish before timing. Input generation and collection construction have separate values. Initial publication includes encoding, two worker deliveries and attachment. The first query requests 1,000 IDs once; the repeat query requests the same IDs. SharedMap can cache decoded JSON locally. Both collection and cache costs remain part of the design.

The update replaces 100 objects and publishes only changed pairs for replica collections, or shared descriptors for SharedMap. Owner update and publication have separate timers, plus a direct timer for the combined operation. All workers retain revision 0 and current revision 1. New and retained answers are checked after timing. Native Map makes one shallow index copy for this first edit, then can edit the current collection in place on later revisions.

Each path uses identical records, IDs, worker counts and validation rules. Paths run in rotating order. Raw JSON includes all samples, source commit and dependency versions. These timings exclude DOM painting and do not measure memory.

HISTORICAL MEMORY · SYNTHETIC RECORDS

Compare memory with reader workers.

The fixed recording uses 100,000 synthetic objects, 1,000 requested IDs, 100 replacements, and the same retained initial revision in every owner and reader. Each comparison below uses the same number of readers. These recordings use an earlier synthetic-record fixture, not the current product catalog. The live size selector does not change this chart.

Recorded runtime baselines: 8ad5788 (two/four readers) and f140ebe (eight readers), with matching library bytes. These figures predate the later main-branch optimizations, including PR30; they do not measure the current live example build.

Both compare medians from three fresh trials with 100,000 synthetic records, 100 replacements and initial/current revisions retained. Retained data and RSS use different accounting; they cannot be added or subtracted to explain the rest of the process. These are endpoint measurements, not peak memory.

Eight readers, recorded separately

The eight-reader run used AMD EPYC 7763 64-Core Processor; the original two/four-reader run used AMD EPYC 9V74 80-Core Processor. Runtime and adapter bytes match, but these are separate cohorts. Compare libraries within each cohort; these panels do not form a controlled same-host scaling curve.
